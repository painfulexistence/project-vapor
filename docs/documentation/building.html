Building & IDE Setup

CMake preset model, per-platform setup, and how to bring your own IDE.

Preset model

CMakePresets.json targets a single generator, Ninja Multi-Config, on every platform. There is no separate Visual Studio solution or Xcode project preset — one build graph, one set of flags to reason about, and Debug/Release/etc. are just --config at build time instead of a reconfigure.

PresetWhat it's for
devConfigure. Everything builds from this — --config Debug / --config Release both work without reconfiguring.
dev / releaseBuild presets — same configure preset, configuration set to Debug / Release.
dev-asanConfigure + build preset with AddressSanitizer instrumentation on the Debug config. Separate binaryDir (build-asan/) so it doesn't fight dev's cache. Not available on Windows (condition excludes it) — MSVC's ASan needs more than a compiler flag to work correctly and hasn't been wired up yet.

vcpkg is a submodule vendored at vcpkg/ — every preset points its toolchain file there, so git clone --recurse-submodules is the only setup a fresh checkout needs before cmake --preset dev works. There's no "global vcpkg install" preset: if you already run vcpkg system-wide for other projects, point CMakeUserPresets.json (gitignored, per-machine, not tracked) at it yourself — see CMake's preset docs for the mechanism.

macOS

brew install ninja ccache
git clone --recurse-submodules https://github.com/painfulexistence/project-vapor
cd project-vapor
cmake --preset dev
cmake --build --preset dev --target main -j4
./build/Vaporware/Debug/main          # Metal
./build/Vaporware/Debug/main --vulkan # Vulkan (MoltenVK)

Linux

sudo apt install ninja-build ccache glslang-tools
git clone --recurse-submodules https://github.com/painfulexistence/project-vapor
cd project-vapor
cmake --preset dev
cmake --build --preset dev --target main -j4
./build/Vaporware/Debug/main --vulkan

Vulkan is the only backend on Linux — there's no Metal, and D3D12 is Windows-only.

Windows

Install the Desktop development with C++ workload from the Visual Studio Installer (this gives you cl.exe, the Windows SDK, and the DirectX 12 headers — you don't need the VS IDE itself, Build Tools alone is enough), plus Ninja and ccache on PATH (winget install Ninja-build.Ninja ccache works).

The one thing that trips people up: Ninja doesn't locate cl.exe the way the old Visual Studio generator did. Opened from a plain terminal, cl.exe isn't on PATH even with VS installed — it lives under a versioned path (...\VC\Tools\MSVC\<ver>\bin\Hostx64\x64\) that only gets added by running vcvarsall.bat first. Two ways to get there:

  • Start Menu → "x64 Native Tools Command Prompt for VS 2022" (installed automatically with the C++ workload) — open it, cd into the repo, run cmake from there.
  • From any existing shell: "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvarsall.bat" x64 (path varies by edition — Community/Professional/BuildTools) before running cmake.

Once the environment is active:

git clone --recurse-submodules https://github.com/painfulexistence/project-vapor
cd project-vapor
cmake --preset dev
cmake --build --preset dev --target main -j4
set VAPOR_DUMP_HLSL=1
.\build\Vaporware\Debug\main.exe --dx12

If you'd rather not think about any of this, open the repo folder directly in Visual Studio 2022 or CLion — both read CMakePresets.json natively and resolve the MSVC environment for you before invoking Ninja, no manual vcvarsall step needed. You get full IntelliSense/debugging through the same Ninja Multi-Config presets everyone else uses; there's no .sln and nothing extra to keep in sync.

Xcode

Not a committed preset — if you want an .xcodeproj for editing/building in Xcode's UI, generate it ad hoc into its own directory (kept separate from build/ so it doesn't collide with the Ninja preset's cache):

cmake -G Xcode -B build-xcode -S . \
  -DCMAKE_TOOLCHAIN_FILE=vcpkg/scripts/buildsystems/vcpkg.cmake
open build-xcode/vapor.xcodeproj

You do not need this just to debug Metal — see below.

GPU debugging

Frame capture doesn't care how the binary was built — a Ninja-built executable is the same binary a VS-generated or Xcode-generated one would be, given the same compiler and flags.

  • RenderDoc (Vulkan, and D3D12 via the UI overlay/injection — in-app capture triggering isn't wired up for D3D12 yet): attach to main.exe --dx12 or main --vulkan same as any other executable.
  • Xcode GPU frame capture (Metal), without an Xcode-generated project: launch the Ninja-built binary with MTL_CAPTURE_ENABLED=1, then in Xcode use Debug → Attach to Process, and Debug → Capture GPU Frame once attached. This is Apple's documented workflow for engines that don't use Xcode as their build system, and it's fully independent of the -G Xcode generator above.
